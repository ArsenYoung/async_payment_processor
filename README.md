# Payment Processing Service

Асинхронный сервис обработки платежей на FastAPI, PostgreSQL и RabbitMQ.

## Текущий статус

Готовы:

- отдельные процессы API, публикатора Outbox и consumer;
- конфигурация через переменные окружения;
- Dockerfile и Docker Compose;
- подключение к PostgreSQL и RabbitMQ;
- модели `Payment` и `Outbox`;
- Alembic-миграции для таблиц `payments`, `outbox` и отметки доставки webhook;
- создание платежей через `POST /api/v1/payments` и получение через `GET /api/v1/payments/{payment_id}`;
- идемпотентное создание платежа и атомарное сохранение платежа вместе с событием Outbox;
- защита операций API и `GET /health` ключом `X-API-Key`, публичная документация с авторизацией в Swagger;
- публикатор Outbox с подтверждением RabbitMQ и корректной остановкой;
- эмулятор шлюза: задержка 2–5 секунд, 90% успешных и 10% неуспешных результатов;
- обработка платежа в `PaymentService`: сохранение итогового статуса и времени обработки, защита от повторного вызова шлюза для завершённого платежа, включая конкурентные вызовы;
- HTTP-клиент webhook: отправка сохранённого результата платежа, таймаут и проверка ответа получателя;
- подписчик `payments.new`: обработка платежа, доставка webhook и сохранение `webhook_delivered_at`;
- автоматические retry с экспоненциальной задержкой и DLQ;
- общие JSON-логи API и воркеров с идентификаторами запросов, платежей и событий;
- автоматические проверки API, обработки и доставки, сквозные Docker-сценарии для `succeeded` и `failed`, проверка запуска на пустой БД и цикла миграций.

После POST публикатор передаёт событие из Outbox в `payments.new`, consumer сохраняет результат шлюза и отправляет webhook. При временной ошибке consumer планирует повтор; после исчерпания трёх попыток событие отправляется в `payments.dlq`. Неповторяемые ошибки направляются в DLQ сразу.

## Фоновые процессы

| Сервис Compose | Роль | Точка запуска |
| --- | --- | --- |
| `outbox-to-rabbitmq-worker` | Выбирает события из PostgreSQL Outbox, публикует в RabbitMQ и сохраняет результат отправки | `payment_processor.outbox_to_rabbitmq_worker.main` |
| `rabbitmq-to-payment-worker` | Обрабатывает `payments.new`, сохраняет результат платежа, отправляет webhook и отмечает доставку | `payment_processor.rabbitmq_to_payment_worker.main` |

Воркеры используют один Docker-образ и запускаются отдельными командами. У каждого свои подключения и обработка сигналов остановки. Публикатор не зависит от запуска consumer.

Платёж и событие Outbox создаются в одной транзакции. Публикатор отправляет устойчивое сообщение в очередь `payments.new` через direct exchange `payments` и отмечает событие опубликованным после подтверждения RabbitMQ. При сбое между подтверждением и commit возможна повторная публикация с тем же `event_id`; для завершённого платежа сервис повторно шлюз не вызывает.

### Настройки обработки и доставки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `OUTBOX_BATCH_SIZE` | `100` | Максимальное число неопубликованных событий в одной партии |
| `OUTBOX_POLL_INTERVAL` | `1.0` | Пауза в секундах после партии или временной ошибки БД |
| `OUTBOX_PUBLISH_TIMEOUT` | `5.0` | Таймаут подтверждённой публикации одного события Outbox в секундах |
| `WEBHOOK_TIMEOUT` | `5.0` | Таймауты подключения, чтения, записи и ожидания соединения HTTP-клиента в секундах |
| `RETRY_BASE_DELAY` | `1.0` | Задержка перед второй попыткой consumer в секундах; перед третьей — удвоенное значение |
| `CONSUMER_PREFETCH_COUNT` | `5` | Максимальное число неподтверждённых сообщений, одновременно выданных consumer |

Все значения должны быть положительными; размеры партий и `CONSUMER_PREFETCH_COUNT` — целыми числами, интервалы и таймауты — конечными числами. Удвоенный `RETRY_BASE_DELAY` также должен быть конечным. Три попытки consumer заданы в коде и не настраиваются через окружение. Таймаут передачи в retry/DLQ составляет 5 секунд и не зависит от `OUTBOX_PUBLISH_TIMEOUT`.

Параметры уже включены в `.env.example` и передаются соответствующему воркеру в `docker-compose.yml`. После изменения `.env` примените их пересозданием нужного контейнера:

```bash
docker compose up -d outbox-to-rabbitmq-worker rabbitmq-to-payment-worker
```

Начальный запуск с миграциями описан в разделе [«Запуск через Docker Compose»](#запуск-через-docker-compose), команды отдельных процессов — в разделе [«Локальный запуск через Poetry»](#локальный-запуск-через-poetry).

### Проверка Outbox

Публикатор выбирает неопубликованные записи вне карантина, у которых наступил `next_attempt_at` или срок ещё не назначен. Порядок — время создания и ID; блокировка — `FOR UPDATE SKIP LOCKED`. Успех увеличивает `attempts`, устанавливает `published_at`, очищает `last_error` и `next_attempt_at`.

Невалидное содержимое события или несовпадающий `payment_id` отправляет запись в карантин: сохраняются `quarantined_at`, причина в `last_error` и увеличенный `attempts`. Полная партия таких записей освобождает путь следующим событиям. Ошибки отправки, включая timeout, отсутствие подтверждения и общий отказ RabbitMQ, назначают повтор через 1, 2, 4, 8, 16, 32, затем 60 секунд. Число повторов не ограничено, инфраструктурные ошибки не отправляют записи в карантин. Неизвестные ошибки отправки также повторяются; их причину следует проверять в логах.

`attempts` считает попытки публикации Outbox и не связан с тремя попытками consumer. Временные ошибки БД повторяются после `OUTBOX_POLL_INTERVAL`. При откате транзакции изменения состояния не сохраняются. Outbox сохраняет проблемные события в PostgreSQL и не отправляет их в DLQ.

После POST задайте `PAYMENT_ID` из ответа и выполните запрос к БД основного Compose-проекта:

```bash
export PAYMENT_ID="d183f5bb-994a-4a68-a433-206ac244b3d2"
docker compose exec -T postgres sh -c \
  'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -v payment_id="$1"' \
  sh "$PAYMENT_ID" <<'SQL'
SELECT p.id AS payment_id, p.status, p.processed_at, p.webhook_delivered_at,
       o.id AS event_id, o.published_at, o.attempts,
       o.next_attempt_at, o.quarantined_at,
       o.last_error IS NOT NULL AS has_publication_error
FROM payments AS p
LEFT JOIN outbox AS o ON o.payment_id = p.id
WHERE p.id = :'payment_id'::uuid;
SQL
```

`published_at` подтверждает сохранение результата публикации в RabbitMQ, но не завершение обработки или webhook. Итог обработки виден в `status` и `processed_at`, сохранённая доставка — в `webhook_delivered_at`. `event_id` совпадает с AMQP `message_id` и связывает запись Outbox с логами consumer и сообщением в DLQ. Если строки нет, проверьте ID и выбранный Compose-проект. Для ошибки публикации найдите в логах `outbox_publish` с тем же `event_id`; способы поиска приведены в разделе [«Логирование и диагностика»](#логирование-и-диагностика).

### Восстановление события из карантина

Найдите `event_id`, `quarantined_at` и причину в `last_error`. Исправьте причину ошибки; при повреждении содержимого подготовьте JSON-файл с полным исправленным `payload` (без оболочки события). Проверьте сумму, валюту и остальные данные по исходному платежу: команда проверяет схему и совпадение `payment_id`, но не сверяет все поля с таблицей платежей.

```bash
poetry run python -m payment_processor.operations.outbox_recovery \
  --event-id "d183f5bb-994a-4a68-a433-206ac244b3d2" \
  --payload-file /path/to/corrected-payload.json
```

Команда использует `DATABASE_URL` из окружения или `.env`. Если содержимое записи уже исправлено, опустите `--payload-file`. Возвращается только выбранное неопубликованное событие в карантине. Проверка и изменение выполняются в одной транзакции с блокировкой строки. Неверный payload, неизвестный ID, опубликованная запись и повторное восстановление завершаются ошибкой.

После успешного восстановления очищаются `quarantined_at` и `next_attempt_at`; `event_id`, `created_at`, `attempts` и последняя причина ошибки сохраняются. Publisher отправит событие при следующем опросе и очистит `last_error` после подтверждённой публикации. Восстановление само по себе не публикует сообщение и не устанавливает `published_at`.

Перед запуском новой версии примените `alembic upgrade head`. Откат этой миграции удаляет сроки повторов и состояние карантина; сохранённые неопубликованные события снова становятся доступны старому publisher. Выполняйте такой откат с остановленным publisher и предварительно разберите карантин.

## Структура проекта

```text
src/payment_processor/
├── api/                         # HTTP API
├── core/                        # конфигурация приложения
├── db/                          # модели, репозитории и сессии PostgreSQL
├── messaging/                   # схемы событий и топология RabbitMQ
├── outbox_to_rabbitmq_worker/    # публикатор PostgreSQL Outbox → RabbitMQ
├── rabbitmq_to_payment_worker/  # обработчик сообщений
└── services/
    ├── payment_service.py
    ├── outbox_service.py
    └── payment_gateway_simulator.py

alembic/
└── versions/     # миграции базы данных
```

`PaymentService` объединяет создание, чтение, обработку платежа и доставку webhook; проверка идемпотентности находится в его закрытых методах. `OutboxService` публикует сохранённые события в RabbitMQ. `PaymentGatewaySimulator` эмулирует внешний шлюз и передаётся в `PaymentService` как зависимость.

При обработке сервис блокирует строку платежа через `SELECT … FOR UPDATE`, вызывает шлюз только для `pending` и сохраняет `succeeded` или `failed` вместе с `processed_at` в UTC. Блокировка удерживается до завершения транзакции. Конкурентный вызов для того же платежа ждёт и затем возвращает сохранённый результат. Техническая ошибка приводит к откату транзакции и передаётся вызывающему коду.

Один подписчик принимает валидируемый `PaymentCreatedEvent` и использует `payment_id` для чтения платежа из БД. Сумма, результат и адрес webhook берутся из сохранённого платежа. Неизвестный платёж приводит к `PaymentNotFoundError`, совместимому с `LookupError`; обработчик классифицирует ошибки и передаёт событие в retry или DLQ.

## Webhook результата платежа

`WebhookClient` отправляет POST на сохранённый `webhook_url` с JSON из завершённого платежа. Пример payload:

```json
{
  "payment_id": "d183f5bb-994a-4a68-a433-206ac244b3d2",
  "status": "succeeded",
  "amount": "10.50",
  "currency": "RUB",
  "description": "Оплата заказа",
  "metadata": {"order_id": "demo-order-001"},
  "created_at": "2026-10-28T10:00:00Z",
  "processed_at": "2026-10-28T10:00:03Z"
}
```

Статус — `succeeded` или `failed`, сумма передаётся строкой без потери точности. Даты и остальные данные берутся из сохранённого платежа. Незавершённый результат отклоняется до HTTP-запроса.

Запрос имеет `Content-Type: application/json`. `payment_id` служит ключом для сопоставления и защиты от повторной обработки у получателя; `event_id` и номер попытки в payload не входят. Клиент не добавляет подпись webhook или заголовок `X-API-Key`. Получатель должен сохранить уведомление и вернуть `2xx`; если он требует дополнительную авторизацию, текущий клиент её не предоставляет.

Успехом считается любой ответ `2xx`; тело ответа не требуется. Перенаправления не выполняются. Остальные HTTP-ответы вызывают `httpx.HTTPStatusError`; сетевые ошибки и таймауты также передаются вызывающему коду. Клиент сам не повторяет отправку. Он используется через `async with`, которое закрывает HTTP-ресурсы при выходе, включая ошибки и отмену задачи.

`WEBHOOK_TIMEOUT` задаёт таймауты отдельных HTTP-операций, а не общий предел времени обработки события. Consumer создаёт один `WebhookClient(timeout=settings.webhook_timeout)` на время работы и закрывает его после остановки брокера, затем освобождает ресурсы БД. `httpx` входит в основные зависимости, устанавливаемые Dockerfile через `poetry install --only main`.

Результат шлюза фиксируется до отправки webhook. Доставка выполняется в отдельной транзакции: сервис заново читает платёж с `SELECT … FOR UPDATE`, проверяет `webhook_delivered_at`, отправляет webhook и сохраняет отметку только после ответа `2xx`. При наличии отметки отправка пропускается. Ошибка уведомления откатывает только транзакцию доставки, сохраняя итоговый статус и `processed_at`.

Получатель webhook должен обрабатывать повторные уведомления идемпотентно по `payment_id`: успешный HTTP-ответ и сохранение отметки доставки в нашей БД не составляют одну атомарную операцию. При повторной доставке события завершённый платёж сохраняет статус и `processed_at`, шлюз не вызывается заново. Если отметки доставки нет, webhook отправляется снова с теми же данными; после commit отметки повторные события пропускают отправку. При конкурентной доставке второй обработчик ждёт блокировку строки и проверяет отметку после завершения транзакции первого.

### Проверка получения webhook

Для ручной проверки основного Docker-окружения используйте приёмник из `tests/e2e/webhook_receiver.py`. После сборки и запуска приложения выполните из корня репозитория в отдельном терминале:

```bash
docker compose run --rm --no-deps --name payment-webhook-demo \
  --publish 127.0.0.1:8081:8081 \
  --volume "$PWD/tests/e2e:/app/e2e:ro" \
  rabbitmq-to-payment-worker \
  uvicorn webhook_receiver:app --app-dir /app/e2e --host 0.0.0.0 --port 8081
```

Команда запускает HTTP-приёмник в сети того же Compose-проекта. В другом терминале задайте `API_KEY` из `.env` и создайте новый платёж; для каждого отдельного запуска выбирайте новый `Idempotency-Key`:

```bash
curl -i -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: ${API_KEY}" \
  -H "Idempotency-Key: delivery-demo-001" \
  -H "Content-Type: application/json" \
  -d '{"amount":"10.50","currency":"RUB","description":"Проверка webhook","metadata":{},"webhook_url":"http://payment-webhook-demo:8081/webhooks"}'
```

Скопируйте ID из ответа `202` и после обработки проверьте уведомления и итоговый платёж:

```bash
export PAYMENT_ID="<payment_id из ответа POST>"
curl -sS "http://localhost:8081/deliveries/${PAYMENT_ID}"
curl -sS -H "X-API-Key: ${API_KEY}" \
  "http://localhost:8000/api/v1/payments/${PAYMENT_ID}"
```

Приёмник отвечает на webhook кодом `204` и хранит полученные payload в памяти. Пустой массив означает, что уведомления ещё нет; повторите GET после обработки. В массиве и ответе платёжного API должны совпадать `payment_id`, итоговый статус, сумма, валюта, описание, metadata и даты. SQL-запрос из раздела «Проверка Outbox» должен показать заполненный `webhook_delivered_at`. Остановите приёмник через `Ctrl+C`; накопленные уведомления при остановке теряются. Он предназначен для локальной проверки и сам не устраняет дубли.

Для consumer, запущенного на хосте через Poetry, можно запустить тот же приёмник командой `poetry run uvicorn webhook_receiver:app --app-dir tests/e2e --host 127.0.0.1 --port 8081` и использовать `webhook_url=http://127.0.0.1:8081/webhooks`. Для consumer в Docker `localhost` относится к его собственному контейнеру; в примере выше используется имя `payment-webhook-demo`.

## Retry и Dead Letter Queue

### Очереди и маршрутизация

| Exchange | Routing key | Очередь | Назначение |
| --- | --- | --- | --- |
| `payments` | `payment.created` | `payments.new` | Первая попытка и обработка вернувшихся retry |
| `payments.retry` | `payment.retry.2` | `payments.retry.2` | Ожидание второй попытки |
| `payments.retry` | `payment.retry.3` | `payments.retry.3` | Ожидание третьей попытки |
| `payments.dead` | `payment.dead` | `payments.dlq` | События с окончательной ошибкой |

Обменники и очереди устойчивые, сообщения публикуются с сохранением на диск, `mandatory=True` и проверкой подтверждения RabbitMQ. Публикатор объявляет основную топологию, consumer — также retry и DLQ. Retry-очереди имеют тип quorum; TTL задаётся на сообщение. После истечения TTL RabbitMQ передаёт событие обратно в `payments` с ключом `payment.created`. Для этого перехода настроены `x-dead-letter-strategy=at-least-once` и `x-overflow=reject-publish`.

### Попытки и ошибки

Всего предусмотрено **три попытки обработки: первая и два повтора**. При временной ошибке на попытке `n` задержка перед следующей составляет `RETRY_BASE_DELAY × 2^(n−1)`:

| Попытка consumer | Предшествующая задержка по умолчанию | При временной ошибке |
| --- | --- | --- |
| 1 | Нет задержки retry | Передача в `payments.retry.2` с задержкой 1 с |
| 2 | 1 с | Передача в `payments.retry.3` с задержкой 2 с |
| 3 | 2 с | Передача в `payments.dlq`, `reason=attempts_exhausted` |

Задержки не включают обработку шлюзом, HTTP-запросы, ожидание очереди и доступности consumer. Если ошибка случилась при webhook, повтор использует сохранённый результат платежа и не вызывает шлюз заново. Бизнес-результат `failed` сам по себе не вызывает retry или DLQ.

Обработчик использует функцию `is_retryable_processing_error` в `services/errors.py` для выбора retry или DLQ. Для повторной попытки подходят исключения HTTP-доставки, включая любой ответ вне `2xx` (в том числе `3xx` и `4xx`), ошибки соединения и таймауты.

Для БД учитываются потеря соединения, исчерпание пула и SQLSTATE ошибок соединения, отката транзакции, нехватки ресурсов, недоступности блокировки и остановки сервера. Если SQLSTATE отсутствует, `OperationalError` и `InterfaceError` считаются повторяемыми; прочие неизвестные ошибки БД — нет. Известные ошибки ограничений, авторизации и SQL не повторяются.

Отсутствующий платёж вызывает `PaymentNotFoundError`, совместимый с `LookupError`; ошибки валидации и программирования не подходят для retry и приводят к передаче события в DLQ. Отмена задачи распространяется без передачи в retry/DLQ.

Номер попытки хранится в AMQP-заголовке `x-payment-attempt`; отсутствие заголовка означает первую попытку. Принимаются только целые числа от 1 до 3. Неверный заголовок или невалидный JSON-контракт события направляются в DLQ сразу с `reason=invalid_message`, без обработки платежа.

Используется `AckPolicy.NACK_ON_ERROR`: исходное сообщение подтверждается после успешного завершения обработчика и commit отметки доставки либо после подтверждённой RabbitMQ публикации в retry/DLQ. Если передача в retry/DLQ не удалась, исключение передаётся FastStream, а исходное сообщение возвращается в очередь с прежним номером попытки. Сбой после подтверждения публикации, но до подтверждения исходного сообщения также допускает дубли. Поэтому три попытки ограничивают последовательность управляемых retry, но не общее число доставок при сбоях. Повторная публикация Outbox тоже может начать доставку с первой попытки для того же события.

При retry/DLQ сохраняются исходное тело события, `message_id`, тип сообщения и `correlation_id`. Попадание в DLQ не меняет статус платежа: при ошибке уведомления он уже может быть `succeeded` или `failed`, а при ошибке до commit обработки — оставаться `pending`.

### Просмотр и диагностика DLQ

Для основного Compose-проекта проверьте очереди:

```bash
docker compose exec -T rabbitmq rabbitmqctl list_queues -p / \
  name messages_ready messages_unacknowledged consumers
```

`messages_ready` показывает ожидающие сообщения, `messages_unacknowledged` — выданные, но ещё не подтверждённые. Retry-очереди могут опустеть до проверки, поскольку задержки короткие. Накопление в `payments.new` без consumers означает, что обработчик не подключён; сообщения в `payments.dlq` требуют диагностики.

Откройте [RabbitMQ Management UI](http://localhost:15672), войдите с `RABBITMQ_USER` и `RABBITMQ_PASSWORD` из `.env`, выберите vhost `/`, затем **Queues and Streams → payments.dlq**. В **Get messages** запросите одно сообщение в режиме с `requeue=true`, чтобы вернуть его в очередь после просмотра. Сопоставьте `message_id` с `event_id` в логах и `payload.payment_id` с платежом. Для некорректного сообщения эти поля могут отсутствовать или не разбираться.

| Заголовок | Значение для диагностики |
| --- | --- |
| `x-payment-attempt` | Текущий номер попытки; в retry — номер следующей попытки |
| `x-payment-failed-attempt` | Попытка, на которой произошла последняя ошибка |
| `x-payment-error-reason` | `attempts_exhausted`, `non_retryable_processing_error` или `invalid_message` для DLQ |
| `x-payment-error-type` | Тип исключения, например `HTTPStatusError` или `ReadTimeout` |
| `x-payment-error-at` | Время последней ошибки в UTC |
| `x-payment-error-http-status` | HTTP-статус, если ошибка вызвана ответом получателя |
| `x-payment-error-sqlstate` | SQLSTATE, если доступен для ошибки БД |
| `x-payment-invalid-attempt` | Исходное значение некорректного заголовка попытки, если он присутствовал |
| `x-death` | История dead-letter переходов RabbitMQ; после retry содержит истечение TTL в retry-очередях |

При исчерпании повторов ожидаются `x-payment-attempt=3`, `x-payment-failed-attempt=3` и `x-payment-error-reason=attempts_exhausted`. Неповторяемая ошибка или неверное сообщение могут попасть в DLQ раньше. Для некорректного заголовка попытки обработчик использует диагностический номер 1 и сохраняет исходное значение отдельно. Текст исключения в диагностические заголовки не копируется.

Чтобы локально проверить попадание в DLQ, запустите описанный выше демонстрационный приёмник и создайте новый платёж с новым `Idempotency-Key` и `webhook_url=http://payment-webhook-demo:8081/missing`. У приёмника нет такого маршрута, поэтому он возвращает `404`; этот ответ считается повторяемой ошибкой. В логах consumer ожидаются две подтверждённые публикации retry, затем `dlq_publish` с `outcome=published`. В UI найдите сообщение с нужным `payment_id` и заголовками третьей попытки, `x-payment-error-http-status=404`. SQL-проверка должна показать итоговый статус шлюза и пустой `webhook_delivered_at`.

Автоматического consumer или возврата сообщений из DLQ нет. Сначала устраните причину, проверьте статус платежа и отметку webhook; ручная повторная публикация требует отдельного решения. Повтор POST с прежним `Idempotency-Key` возвращает существующий платёж и не создаёт новое событие Outbox, поэтому не запускает доставку из DLQ заново.

Автоматические проверки этого поведения находятся в `tests/test_retry_routing.py`, `tests/test_dead_letter_queue.py` и `tests/test_payment_retries.py`; сквозную проверку успешного получения webhook запускайте командой `RUN_E2E=1 poetry run pytest -q tests/e2e/test_payment_flow.py` из раздела [«Проверки качества»](#проверки-качества).

После миграций соберите образ и запустите API отдельно:

```bash

```

Миграции при запуске контейнеров автоматически не применяются. Воркеры можно запустить
после восстановления RabbitMQ; они отправят накопленные события Outbox:


Ожидаемый результат:

- PostgreSQL — `healthy`;
- RabbitMQ — `healthy`;
- API — `healthy`;
- `outbox-to-rabbitmq-worker` — запущен;
- `rabbitmq-to-payment-worker` — запущен.

Остановить сервисы и удалить контейнеры и сеть проекта:

```bash
docker compose down
```

Данные PostgreSQL и RabbitMQ хранятся в именованных томах `postgres_data` и `rabbitmq_data`. RabbitMQ использует стабильное имя узла `rabbit@rabbitmq`, чтобы после пересоздания контейнера открыть прежние данные. Обычный `down` сохраняет тома: платежи, неопубликованный Outbox и устойчивые сообщения очереди остаются для следующего запуска.

Повторно запустить сервисы:

```bash
docker compose up -d --wait
```

Используйте прежнее имя Compose-проекта: от него зависят имена томов. При запуске из другой директории задайте прежнее имя через `docker compose -p <имя-проекта> ...`. Для короткой паузы без удаления контейнеров можно использовать `docker compose stop` и затем `docker compose start`.

Если окружение уже запускалось до добавления именованных томов, существующие данные из анонимных томов автоматически не переносятся. До пересоздания прежних контейнеров сохраните резервную копию PostgreSQL и ожидающие сообщения RabbitMQ и подготовьте их перенос. Команды ниже не являются процедурой переноса.

Намеренно удалить все данные текущего проекта вместе с контейнерами:

```bash
docker compose down --volumes
```

Эта команда удаляет платежи, Outbox и состояние RabbitMQ. После следующего запуска PostgreSQL будет пустым, поэтому миграции нужно применить заново до запуска API и воркеров по инструкции выше.

## API платежей

### Создание платежа

Для нового платежа нужны `X-API-Key`, `Idempotency-Key` и JSON-тело. Сначала запустите сервисы и задайте `API_KEY`, как показано выше.

В примере замените `https://example.com/webhook` адресом своего получателя: этот URL служит образцом и не принимает уведомления вашего приложения. Получатель должен быть доступен из процесса consumer и возвращать `2xx`. В Docker адрес `localhost` указывает на сам контейнер consumer.

Сохраните тело запроса для проверки повторов. Ключ `demo-order-001` должен быть новым для первого запуска примера; для следующего отдельного платежа выберите другой ключ.

```bash
export IDEMPOTENCY_KEY="demo-order-001"
export PAYMENT_PAYLOAD='{
  "amount": "10.50",
  "currency": "RUB",
  "description": "Оплата заказа",
  "metadata": {"order_id": "demo-order-001"},
  "webhook_url": "https://example.com/webhook"
}'
curl -i -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: ${API_KEY}" \
  -H "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  -H "Content-Type: application/json" \
  -d "${PAYMENT_PAYLOAD}"
```

Первый запрос возвращает `202 Accepted`. Пример тела ответа; идентификатор и время будут другими:

```json
{
  "payment_id": "d183f5bb-994a-4a68-a433-206ac244b3d2",
  "status": "pending",
  "created_at": "2026-10-28T10:00:00Z"
}
```

Ответ `202` означает, что платёж и событие Outbox сохранены. Обработка шлюзом и отправка webhook выполняются асинхронно.

### Получение платежа

Скопируйте `payment_id` из ответа POST в переменную `PAYMENT_ID`:

```bash
export PAYMENT_ID="d183f5bb-994a-4a68-a433-206ac244b3d2"
curl -i -H "X-API-Key: ${API_KEY}" \
  "http://localhost:8000/api/v1/payments/${PAYMENT_ID}"
```

Успешный ответ — `200 OK`. Пример до завершения обработки; `webhook_url` соответствует адресу из вашего POST:

```json
{
  "payment_id": "d183f5bb-994a-4a68-a433-206ac244b3d2",
  "status": "pending",
  "created_at": "2026-10-28T10:00:00Z",
  "amount": "10.50",
  "currency": "RUB",
  "description": "Оплата заказа",
  "metadata": {"order_id": "demo-order-001"},
  "idempotency_key": "demo-order-001",
  "webhook_url": "https://example.com/webhook",
  "processed_at": null
}
```

Для GET заголовок `Idempotency-Key` не нужен. При работающих публикаторе и consumer платёж завершается автоматически, поэтому уже первый GET может вернуть итоговый статус. Повторите GET после обработки. Пример успешного результата:

```json
{
  "payment_id": "d183f5bb-994a-4a68-a433-206ac244b3d2",
  "status": "succeeded",
  "created_at": "2026-10-28T10:00:00Z",
  "amount": "10.50",
  "currency": "RUB",
  "description": "Оплата заказа",
  "metadata": {"order_id": "demo-order-001"},
  "idempotency_key": "demo-order-001",
  "webhook_url": "https://example.com/webhook",
  "processed_at": "2026-10-28T10:00:03Z"
}
```

| Статус | Значение | `processed_at` |
| --- | --- | --- |
| `pending` | Платёж ожидает результата шлюза | `null` |
| `succeeded` | Шлюз одобрил платёж | Время обработки в UTC |
| `failed` | Шлюз отклонил платёж | Время обработки в UTC |

GET возвращает `200` для всех трёх статусов. `failed` — итог обработки платежа. Ошибка webhook не меняет итоговый статус; наличие `processed_at` само по себе не подтверждает доставку уведомления. Сумма в ответе передаётся строкой, даты — в формате ISO 8601.

### Идемпотентность POST

Повторите запрос с сохранёнными ключом и телом:

```bash
curl -i -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: ${API_KEY}" \
  -H "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  -H "Content-Type: application/json" \
  -d "${PAYMENT_PAYLOAD}"
```

Ответ снова имеет код `202 Accepted` и содержит исходные `payment_id` и `created_at`, а также текущий статус платежа. После обработки статус может быть `succeeded` или `failed`. Новые платёж и событие Outbox не создаются, повтор POST не запускает обработку заново.

Сравниваются все поля тела: `amount`, `currency`, `description`, `metadata` и `webhook_url`. Сравнение выполняется после валидации: суммы `10.5` и `10.50` равны, пропущенное `metadata` эквивалентно `{}`, URL сравнивается в нормализованном Pydantic виде. В `metadata` порядок ключей JSON-объекта значения не имеет, а порядок элементов массива значим. JSON boolean сравнивается отдельно от числа: `true` не равен `1`, `false` не равен `0`, в том числе во вложенных объектах и массивах. Числа сравниваются по значению, поэтому `1` и `1.0` считаются равными независимо от способа сериализации.

Для проверки конфликта отправьте тот же ключ с другой суммой. В `webhook_url` укажите тот же адрес, который использовали при создании:

```bash
curl -i -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: ${API_KEY}" \
  -H "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": "11.50",
    "currency": "RUB",
    "description": "Оплата заказа",
    "metadata": {"order_id": "demo-order-001"},
    "webhook_url": "https://example.com/webhook"
  }'
```

Ответ — `409 Conflict`:

```json
{"detail":"Idempotency key was used with a different request"}
```

Исходный платёж остаётся прежним. Для нового платежа нужен новый ключ. При конкурентных запросах с одинаковыми ключом и данными создаётся один платёж; при различающихся данных один запрос создаёт платёж, другой получает `409`.

### Валидация и ошибки

| Поле или заголовок | Обязателен | Ограничения |
| --- | --- | --- |
| `X-API-Key` | Да, для POST и GET | Должен совпадать с `API_KEY` сервиса |
| `Idempotency-Key` | Да, для POST | Строка от 1 до 255 символов |
| `amount` | Да | Положительное десятичное число: до 18 цифр всего, до 16 в целой части и до 2 после точки; в примерах передаётся строкой |
| `currency` | Да | `RUB`, `USD` или `EUR`, с учётом регистра |
| `description` | Да | Строка от 1 до 500 символов |
| `metadata` | Нет | JSON-объект, по умолчанию `{}`; допускаются вложенные JSON-значения |
| `webhook_url` | Да | HTTP(S)-адрес с хостом, до 2048 символов после нормализации |
| `payment_id` в пути GET | Да | Корректный UUID |

Дополнительные поля тела POST отклоняются. В описании, ключе идемпотентности, ключах и строковых значениях `metadata` запрещены нулевой символ и некорректный Unicode. Числа в `metadata` должны быть конечными; `NaN` и бесконечность отклоняются.

| Код | Причина |
| --- | --- |
| `401 Unauthorized` | Отсутствует или неверен `X-API-Key` |
| `404 Not Found` | В GET указан корректный UUID, но платёж не найден |
| `409 Conflict` | Ключ идемпотентности уже использован с другими данными |
| `422 Unprocessable Entity` | Неверное тело POST, отсутствует или некорректен `Idempotency-Key`, либо некорректен UUID в GET |

Тело ответа `401`:

```json
{"detail":"Invalid API key"}
```

Тело ответа `404`:

```json
{"detail":"Payment not found"}
```

Для проверки `422` отправьте корректное тело без `Idempotency-Key`:

```bash
curl -i -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d "${PAYMENT_PAYLOAD}"
```

Ответ — `422 Unprocessable Entity`:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["header", "Idempotency-Key"],
      "msg": "Field required"
    }
  ]
}
```

Ошибки валидации содержат `type`, `loc` и `msg`; исходные значения запроса в ответ не включаются. В `loc` источник ошибки обозначен как `header`, `body` или `path`. Например, сумма `10.123` приводит к ошибке поля `amount`, а GET с `payment_id=not-a-uuid` — к ошибке параметра пути.

```bash
RUN_DOCKER_SMOKE=1 poetry run pytest -q tests/smoke/test_data_persistence.py
```

Проверка создаёт отдельный Compose-проект со случайным именем, собственными томами, тестовыми учётными данными и свободными локальными портами. Используется основной `docker-compose.yml`; тест меняет только порты и имя образа, добавляет получателя webhook и подключает миграции к одноразовому контейнеру. Рабочая `.env` не используется для Docker-окружения. Нужны доступ к Docker и возможность собрать образ. После проверки удаляются только ресурсы тестового проекта.

Два сценария проверяют сохранение платежа и события при `down/up`: с уже опубликованным сообщением в RabbitMQ и с неопубликованным Outbox при остановленном publisher. После запуска воркеров проверяются итог платежа и фактический webhook. Без `RUN_DOCKER_SMOKE=1` эти Docker-сценарии пропускаются.

Перед запуском тестов настройте `.env`, запустите PostgreSQL и RabbitMQ и примените миграции. Интеграционные тесты используют реальные подключения: часть создаёт записи с уникальными ключами в настроенной БД и удаляет их после проверки, часть — временные схемы PostgreSQL и отдельные очереди и обменники RabbitMQ.

Покрыты создание и получение платежей со всеми тремя статусами, авторизация, валидация, идемпотентность и конкурентные запросы, атомарность платежа и Outbox, публикация и восстановление после сбоев, жизненный цикл API и воркеров. Тесты эмулятора проверяют задержки и оба результата без реального ожидания; тесты обработки — сохранение результата, повторные и конкурентные вызовы, откат при ошибках шлюза, commit и отмене задачи. Есть проверки webhook, автоматических retry, экспоненциальных задержек, предела попыток, DLQ и логирования. HTTP в интеграционных тестах webhook заменён через `httpx.MockTransport`.

Запустить только проверки API из примеров выше:

```bash
poetry run pytest -q tests/test_payment_creation.py tests/test_payment_retrieval.py tests/test_payment_validation.py tests/test_payment_idempotency.py
```

Docker-проверки по умолчанию пропускаются. Они требуют работающего Docker Engine, Compose и возможности собрать образ приложения. Каждая проверка поднимает отдельный Compose-проект с собственными PostgreSQL и RabbitMQ, динамическими портами и тестовыми настройками из `docker-compose.test.yml`. Миграции выполняются внутри тестового контейнера с подключёнными файлами Alembic. Заранее запускать основной Compose-проект и применять миграции в рабочей БД для этих проверок не нужно. После проверки тестовый проект и его ресурсы удаляются.

Сквозной сценарий POST → Outbox → RabbitMQ → consumer → HTTP webhook → GET:

```bash
RUN_E2E=1 poetry run pytest -q tests/e2e/test_payment_flow.py
```

Сценарии используют реальный HTTP-приёмник webhook и управляемый эмулятор шлюза для обоих исходов: `succeeded` и `failed`. Они проверяют первоначальный `pending`, совпадение webhook с итоговым GET и сохранение ID при повторном POST.

Сборка образа, наличие runtime-зависимостей, пустая БД, цикл `upgrade head` → `downgrade base` → `upgrade head`, отсутствие расхождений моделей и миграций, готовность API и штатных воркеров:

```bash
RUN_DOCKER_SMOKE=1 poetry run pytest -q tests/smoke/test_docker_setup.py
```

## Логирование и диагностика

### Уровень и формат логов

API и оба воркера пишут в stdout: одна JSON-запись на строку. `LOG_LEVEL` задаёт минимальный уровень, по умолчанию `INFO`. Допустимы `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`; регистр и пробелы по краям нормализуются, неизвестное значение отклоняется при загрузке настроек. Compose передаёт настройку всем трём процессам. При локальном запуске она читается из окружения или `.env`; изменение применяется при следующем запуске процесса. После изменения `.env` в Docker выполните:

```bash
docker compose up -d api outbox-to-rabbitmq-worker rabbitmq-to-payment-worker
```

`INFO` подходит для поиска всей истории платежа: видны HTTP-запросы, запуск и остановка воркеров, публикация, обработка и доставка. `WARNING` показывает временные ошибки и запланированные повторы; `ERROR` — в том числе передачу в DLQ и сбой публикации в retry/DLQ. Уровни `WARNING` и выше скрывают успешные этапы. Обычные HTTP-ответы `401`, `404`, `409` и `422` записываются на `INFO`; необработанные исключения API — на `ERROR`. Пустые опросы Outbox не создают записей. Для библиотек подключений и HTTP-клиента минимальный уровень — `WARNING`, даже при `LOG_LEVEL=DEBUG`.

| Поля | Значение |
| --- | --- |
| `timestamp`, `level` | Время UTC с миллисекундами и суффиксом `Z`; уровень записи |
| `component` | `api`, `outbox-to-rabbitmq-worker` или `rabbitmq-to-payment-worker` |
| `logger`, `message` | Имя логгера и описание действия |
| `request_id` | Сгенерированный API идентификатор HTTP-запроса; возвращается в заголовке ответа `X-Request-ID` |
| `method`, `path`, `status_code` | Метод, путь без query-параметров и код HTTP-ответа; для `webhook_http` код относится к получателю webhook |
| `duration_ms` | Длительность соответствующего запроса или операции в миллисекундах |
| `payment_id`, `event_id` | Идентификаторы платежа и события Outbox; связывают этапы обработки и повторы |
| `worker` | Имя воркера в записях запуска и остановки |
| `queue`, `operation`, `outcome` | Очередь, этап и его результат; в `retry_publish`/`dlq_publish` очередь обозначает назначение публикации |
| `publication_attempt` | Номер попытки публикации Outbox, начиная с 1; соответствует увеличению `outbox.attempts` при сохранении результата |
| `attempt` | Текущая попытка consumer/webhook от 1 до 3; независима от `publication_attempt` |
| `next_attempt`, `retry_delay_ms` | Следующая попытка и задержка перед ней; присутствуют при публикации в retry |
| `payment_status` | Сохранённый результат платежа: `succeeded` или `failed` |
| `reason`, `error_type` | Категория причины и имя класса исключения |
| `exception` | Тип исключения и traceback: файл, строка, функция; при наличии — цепочка причин или вложенные исключения |

Поля `timestamp`, `level`, `component`, `logger`, `message` присутствуют в каждой записи; остальные добавляются при наличии контекста. API записывает `payment_id`, когда он известен маршруту, но не передаёт `request_id` в событие Outbox. Поэтому переход от HTTP к воркерам выполняется по `payment_id`, а между Outbox, consumer и повторами — также по `event_id`. При некорректном сообщении `payment_id` может отсутствовать; `event_id` берётся из `message_id`, если это корректный UUID.

### Просмотр и поиск

Команды выполняются из корня проекта. Для фильтрации ниже нужен `rg` (ripgrep) на хосте. Посмотреть последние записи трёх процессов и продолжить наблюдение:

```bash
docker compose logs --tail=100 --follow api outbox-to-rabbitmq-worker rabbitmq-to-payment-worker
```

Для отдельного этапа укажите только нужный сервис:

```bash
docker compose logs --since=15m --tail=100 outbox-to-rabbitmq-worker
docker compose logs --since=15m --tail=100 rabbitmq-to-payment-worker
```

Найти историю платежа за последний час. Замените вымышленный UUID значением `payment_id` из ответа POST:

```bash
PAYMENT_ID='d183f5bb-994a-4a68-a433-206ac244b3d2'
docker compose logs --since=1h --no-color --no-log-prefix api outbox-to-rabbitmq-worker rabbitmq-to-payment-worker \
  | rg -F -- "$PAYMENT_ID"
```

В найденной записи `outbox_publish` или `consume` возьмите `event_id`, чтобы проследить конкретное событие, включая retry и DLQ:

```bash
EVENT_ID='a1e6cf84-7baa-4cea-8a93-787b8886d6ee'
docker compose logs --since=1h --no-color --no-log-prefix outbox-to-rabbitmq-worker rabbitmq-to-payment-worker \
  | rg -F -- "$EVENT_ID"
```

Найти запрос API, в том числе ошибку до определения платежа, можно по `X-Request-ID` из ответа:

```bash
REQUEST_ID='9307e7ca-32e2-4bc8-a880-37a714de4e20'
docker compose logs --since=1h --no-color --no-log-prefix api \
  | rg -F -- "$REQUEST_ID"
```

`--no-color` и `--no-log-prefix` убирают оформление Compose, сохраняя JSON приложения. Интервал `--since` следует увеличить, если платёж создан раньше. Отсутствие записей также возможно при уровне выше `INFO` или после удаления контейнера и его логов.

### Как читать историю платежа

| Этап (`operation`) | Результат (`outcome`) и смысл |
| --- | --- |
| HTTP-запрос API, без `operation` | `HTTP request completed`: проверяйте `status_code`, `request_id` и доступный `payment_id` |
| `outbox_publish` | `published`: RabbitMQ подтвердил публикацию и транзакция Outbox завершилась; `failed`: ошибка публикации сохранена; `transaction_failed`: транзакция не завершилась, счётчик попыток мог откатиться |
| `consume` | `received`: сообщение принято; `completed`: обработка и доставка завершились; `failed`: обработчик выбрал retry или DLQ по `reason` |
| `payment_process` | `processed`: результат шлюза сохранён; `already_processed`: использован сохранённый результат без нового вызова шлюза; `failed`: техническая ошибка |
| `webhook_http` | `accepted`: получен `2xx`; `failed`: ошибка запроса или ответ вне `2xx`, при полученном ответе есть `status_code` |
| `webhook_delivery` | `delivered`: отметка доставки сохранена после commit; `already_delivered`: отправка пропущена по сохранённой отметке; `failed`: доставка или её сохранение завершились ошибкой |
| `retry_publish` | `published`: RabbitMQ подтвердил передачу в очередь следующей попытки; `failed`: передача не подтверждена |
| `dlq_publish` | `published`: RabbitMQ подтвердил передачу в `payments.dlq`; запись имеет уровень `ERROR`; `failed`: передача в DLQ не удалась |

`payment_status=failed` — завершённый бизнес-результат шлюза. Он допускает успешную доставку webhook и `consume` с `outcome=completed`.

Пример записи об успешном HTTP-запросе API; все идентификаторы и времена в примерах вымышлены:

```json
{"timestamp":"2026-10-29T10:00:00.125Z","level":"INFO","component":"api","logger":"payment_processor.api.middleware","message":"HTTP request completed","request_id":"9307e7ca-32e2-4bc8-a880-37a714de4e20","method":"POST","path":"/api/v1/payments","status_code":202,"duration_ms":12.5,"payment_id":"d183f5bb-994a-4a68-a433-206ac244b3d2"}
```

Если первая отправка webhook получила `503`, ищите `webhook_http` с `outcome=failed`, `status_code=503`, `error_type=HTTPStatusError`, затем `webhook_delivery` и `consume` с ошибкой. Подтверждённый повтор для того же платежа и события выглядит так:

```json
{"timestamp":"2026-10-29T10:00:03.250Z","level":"WARNING","component":"rabbitmq-to-payment-worker","logger":"payment_processor.messaging.topology","message":"Payment retry scheduled","payment_id":"d183f5bb-994a-4a68-a433-206ac244b3d2","event_id":"a1e6cf84-7baa-4cea-8a93-787b8886d6ee","queue":"payments.retry.2","operation":"retry_publish","outcome":"published","attempt":1,"next_attempt":2,"retry_delay_ms":1000.0,"reason":"retryable_processing_error","error_type":"HTTPStatusError","duration_ms":4.0}
```

При следующей обработке `consume` показывает `attempt=2`, а `payment_process` — `already_processed`: итог платежа уже сохранён. После успешного webhook ожидаются `webhook_http` с `accepted`, `webhook_delivery` с `delivered` и `consume` с `completed`. Сам по себе `webhook_http` с `accepted` ещё не подтверждает commit отметки доставки; при сбое commit возможна повторная отправка.

### Диагностика сбоев

- **Outbox:** найдите `outbox_publish` с `failed`, его `error_type` и `exception`. Проверьте доступность RabbitMQ и объявление очереди `payments.new`; после восстановления ожидается `published` с тем же `event_id` и увеличенным `publication_attempt`. При `transaction_failed` результат не зафиксирован, а подтверждённая брокером публикация могла уже произойти. `outbox_poll` с `reason=database_unavailable` указывает на недоступность БД; такая запись может не содержать идентификаторов платежа или события.
- **Webhook:** по `webhook_http` различайте HTTP-ошибку с `status_code` и сетевую ошибку/таймаут по `error_type`. Проверьте доступность получателя из сети consumer и его собственные логи. Ошибка webhook не отменяет сохранённый статус платежа; если HTTP принят, но `webhook_delivery` завершилась ошибкой, проверьте сохранение в БД.
- **Retry:** `consume` с `reason=retryable_processing_error` означает выбор повтора. Его подтверждает только `retry_publish` с `outcome=published`, очередью `payments.retry.2` или `payments.retry.3`, `next_attempt` и `retry_delay_ms`. Задержка относится к ожиданию в retry; время до начала обработки зависит также от очереди и доступности consumer. Повторные доставки при сбое публикации или подтверждения могут повторять один номер `attempt`.
- **DLQ:** `reason=attempts_exhausted` означает, что временная ошибка сохранилась на третьей попытке; `non_retryable_processing_error` — ошибку без повтора; `invalid_message` — некорректное тело события или заголовок попытки. Ищите подтверждение `dlq_publish` с `outcome=published`, `queue=payments.dlq` и тем же `event_id`. В RabbitMQ Management UI откройте очередь `payments.dlq`, чтобы проверить число сообщений; автоматического возврата из неё нет.
- **Сбой передачи в retry/DLQ:** `retry_publish` или `dlq_publish` с `outcome=failed` показывает ошибку самой публикации в `error_type` и `exception`. Запись `consume` с ошибкой ещё не доказывает передачу. Исходное сообщение возвращается в очередь; проверьте RabbitMQ и дождитесь записи `published` либо успешного завершения обработки.

### Чувствительные данные

Прикладные записи не включают ключи и секретные заголовки, пароли и строки подключения с учётными данными, `metadata`, тела запросов и ответов, payload webhook и полный webhook URL. Query-параметры HTTP-запроса не записываются. Форматтер маскирует известные значения настроек `API_KEY`, `DATABASE_URL`, `RABBITMQ_URL`, пароли из этих URL, адреса URL и чувствительные поля в сообщениях.

В `exception` сохраняются типы и расположение кадров traceback; тексты исключений, строки исходного кода и локальные переменные исключены. Для диагностики используйте `error_type`, `reason`, `status_code`, идентификаторы и кадры traceback. `DEBUG` не отключает фильтрацию чувствительных данных.
