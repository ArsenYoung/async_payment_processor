# Модель доставки webhook

Webhook остаётся частью обработки `payment.created`: consumer сначала сохраняет результат платежа, затем отправляет единственное итоговое уведомление. Retry и DLQ управляют повтором всего сообщения; завершённый платёж повторно не обрабатывается шлюзом. Номер попытки consumer не равен числу HTTP-запросов: ошибка может возникнуть до отправки webhook, а broker redelivery может повторить тот же номер.

## Хранение состояния

Отдельная таблица `webhook_deliveries` в текущей модели не вводится. Доставка ещё не является самостоятельным процессом с историей попыток, отдельным расписанием и собственным жизненным циклом. Создание таблицы сейчас дублировало бы состояние платежа и retry-сообщения, не предоставляя такой истории.

Существующие данные имеют следующие значения:

- `payments.webhook_delivered_at` подтверждает успешный HTTP-ответ и сохранение результата доставки в БД;
- webhook lease с UUID владельца и сроком защищает короткие транзакции захвата и подтверждения от конкурирующих и устаревших обработчиков;
- заголовки retry/DLQ содержат номер попытки consumer, тип последней ошибки и HTTP status для HTTP-ошибок;
- задержка следующей попытки определяется retry policy и TTL сообщения RabbitMQ; отдельного `next_attempt_at` webhook в БД нет;
- логи позволяют сопоставить HTTP-вызовы и обработку платежа, но не являются транзакционной историей доставки.

Границы транзакций, fencing и ограничения lease описаны в [transaction-boundaries.md](transaction-boundaries.md). HTTP-запрос выполняется без открытой DB-транзакции. Если получатель принял уведомление, а отправитель не смог сохранить отметку, уведомление будет отправлено повторно. Lease не исключает повторный внешний эффект после истечения срока или потери подтверждения.

## Условия выделения самостоятельного процесса

Таблица потребуется при появлении независимого webhook worker, просмотра истории попыток, нескольких подписчиков или ручного повторного запуска доставки. Тогда нужно отдельно определить устойчивый delivery/event id и записи попыток с payment id, номером HTTP-попытки, статусом, HTTP status, временем следующей попытки и последней ошибкой. Номер HTTP-попытки должен назначаться транзакционно и не копироваться из заголовка попытки consumer.

Выделение этого процесса потребует стратегии атомарного создания задания, lease и восстановления незавершённых попыток. Текущий блок не меняет схему БД и не обещает историю попыток, которой сейчас нет.


## Контракт идемпотентности получателя

Каждый POST содержит `X-Webhook-Delivery-Id: <payment UUID>`. Сейчас для платежа существует одно итоговое уведомление, поэтому delivery id равен канонической строке `payment_id` из JSON. Он сохраняется при повторе, broker redelivery, потере HTTP-ответа, неуспешной фиксации отметки доставки и перезапуске клиента. Разные платежи имеют разные delivery id. Это идентификатор итогового уведомления, а не номер HTTP-попытки и не event id входного `payment.created`.

Тело JSON и формат его полей не меняются; новые поля в payload не добавляются. Существующие получатели могут продолжать использовать `payment_id` для дедупликации. Если в будущем у платежа появятся несколько видов уведомлений или адресатов, потребуется новая модель идентификаторов и отдельное согласование контракта.

Получатель обязан:

1. Проверить уведомление и атомарно сохранить delivery id вместе с изменением своего бизнес-состояния, например через уникальный ключ в той же транзакции.
2. При повторном или конкурентном запросе с тем же ID не выполнять бизнес-операцию повторно и вернуть успешный `2xx`. Если первая операция ещё выполняется, подтвердить повтор только после её успешного сохранения.
3. Отправлять `2xx` после надёжного сохранения уведомления или его постановки в собственную устойчивую очередь. Получатель отвечает за дальнейшую обработку принятого задания.

Если бизнес-эффект выполняется во внешней системе, одной записи ID до вызова недостаточно: получатель должен обеспечить восстановление незавершённой операции или передать ключ идемпотентности дальше. При сбое между внешним эффектом и сохранением ID возможны дубликаты.

Отправитель принимает только успешный `2xx`, не следует redirect и не выполняет скрытые повторы HTTP внутри клиента. Retry consumer применяется к timeout, сетевым ошибкам и повторяемым HTTP-ошибкам согласно существующему классификатору; исчерпанные попытки уходят в DLQ. Точная классификация приведена в README. Сам delivery id не аутентифицирует запрос; подпись или управление секретами этим изменением не вводятся.
