# Outbox и восстановление

### Проверка Outbox

Публикатор выбирает неопубликованные записи вне карантина, у которых наступил `next_attempt_at` или срок ещё не назначен. Порядок — время создания и ID; блокировка — `FOR UPDATE SKIP LOCKED`. Успех увеличивает `attempts`, устанавливает `published_at`, очищает `last_error` и `next_attempt_at`.

Невалидное содержимое события или несовпадающий `payment_id` отправляет запись в карантин: сохраняются `quarantined_at`, причина в `last_error` и увеличенный `attempts`. Полная партия таких записей освобождает путь следующим событиям. Ошибки отправки, включая timeout, отсутствие подтверждения и общий отказ RabbitMQ, назначают повтор через 1, 2, 4, 8, 16, 32, затем 60 секунд. Число повторов не ограничено, инфраструктурные ошибки не отправляют записи в карантин. Неизвестные ошибки отправки также повторяются; их причину следует проверять в логах.

`attempts` считает попытки публикации Outbox и не связан с тремя попытками consumer. Временные ошибки БД повторяются после `OUTBOX_POLL_INTERVAL`. При откате транзакции изменения состояния не сохраняются. Outbox сохраняет проблемные события в PostgreSQL и не отправляет их в DLQ.

После POST задайте `PAYMENT_ID` из ответа и выполните запрос к БД основного Compose-проекта:

```bash
export PAYMENT_ID="d183f5bb-994a-4a68-a433-206ac244b3d2"
docker compose exec -T postgres sh -c \
  'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -v payment_id="$1"' \
  sh "$PAYMENT_ID" <<'SQL'
SELECT p.id AS payment_id, p.status, p.processed_at, p.webhook_delivered_at,
       o.id AS event_id, o.published_at, o.attempts,
       o.next_attempt_at, o.quarantined_at,
       o.last_error IS NOT NULL AS has_publication_error
FROM payments AS p
LEFT JOIN outbox AS o ON o.payment_id = p.id
WHERE p.id = :'payment_id'::uuid;
SQL
```

`published_at` подтверждает сохранение результата публикации в RabbitMQ, но не завершение обработки или webhook. Итог обработки виден в `status` и `processed_at`, сохранённая доставка — в `webhook_delivered_at`. `event_id` совпадает с AMQP `message_id` и связывает запись Outbox с логами consumer и сообщением в DLQ. Если строки нет, проверьте ID и выбранный Compose-проект. Для ошибки публикации найдите в логах `outbox_publish` с тем же `event_id`; способы поиска приведены в документе [«Логирование и диагностика»](diagnostics.md).

### Восстановление события из карантина

Найдите `event_id`, `quarantined_at` и причину в `last_error`. Исправьте причину ошибки; при повреждении содержимого подготовьте JSON-файл с полным исправленным `payload` (без оболочки события). Проверьте сумму, валюту и остальные данные по исходному платежу: команда проверяет схему и совпадение `payment_id`, но не сверяет все поля с таблицей платежей.

```bash
poetry run python -m payment_processor.operations.outbox_recovery \
  --event-id "d183f5bb-994a-4a68-a433-206ac244b3d2" \
  --payload-file /path/to/corrected-payload.json
```

Команда использует `DATABASE_URL` из окружения или `.env`. Если содержимое записи уже исправлено, опустите `--payload-file`. Возвращается только выбранное неопубликованное событие в карантине. Проверка и изменение выполняются в одной транзакции с блокировкой строки. Неверный payload, неизвестный ID, опубликованная запись и повторное восстановление завершаются ошибкой.

После успешного восстановления очищаются `quarantined_at` и `next_attempt_at`; `event_id`, `created_at`, `attempts` и последняя причина ошибки сохраняются. Publisher отправит событие при следующем опросе и очистит `last_error` после подтверждённой публикации. Восстановление само по себе не публикует сообщение и не устанавливает `published_at`.

Начальная ревизия `20261101a001` включает сроки повторов, карантин и leases. Применяйте `alembic upgrade head` к новой пустой БД. Откат до `base` удаляет таблицы платежей и Outbox, поэтому проверяйте его только на одноразовой тестовой БД. Перенос данных из БД со старой историей миграций требует отдельного согласованного плана; остановки publisher недостаточно для безопасного отката.
