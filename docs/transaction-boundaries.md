# Границы транзакций

## Обработка платежа

Короткая транзакция читает платеж с row lock и закрепляет processing lease на 60 секунд за уникальным UUID владельца. Конкурентный обработчик повторяет короткое чтение через 250 мс, освобождая соединение между проверками. Ожидание, включая запросы и commit захвата, ограничено 5 секундами. При исчерпании срока `LeaseBusyError` направляет сообщение в существующий retry. Завершенный платеж возвращается без gateway-вызова.

Gateway вызывается после commit захвата, без открытой DB-транзакции. Вызов ограничен 30 секундами. Ключ идемпотентности — UUID платежа: повторный вызов, включая восстановление после падения процесса или неясного результата commit, обязан возвращать результат той же операции без повторного списания. Любая новая реализация gateway должна обеспечивать этот контракт на стороне провайдера.

Симулятор вычисляет исход по SHA-256 UUID и настроенному success rate, поэтому результат сохраняется между экземплярами и перезапусками при одинаковой конфигурации. Случайная задержка сохраняется. Вызов симулятора без ключа оставлен для самостоятельного тестирования распределения исходов.

Отдельная транзакция проверяет токен и срок lease, сохраняет доменный результат и освобождает lease. Проверка берет row lock до commit: устаревший владелец не может перезаписать результат нового обработчика. При исключении или отмене выполняется условное освобождение только своего токена. Если БД недоступна или процесс завершился, lease становится доступен после истечения срока. Для сроков используется время PostgreSQL.

## Доставка webhook

Delivery lease использует отдельные токен и срок, независимо от обработки платежа. Первая короткая транзакция читает платеж и закрепляет владельца. После ее commit создается snapshot, и HTTP-запрос выполняется без транзакции и занятого соединения. Второй конкурентный запрос ожидает освобождения или истечения lease, затем повторно проверяет отметку доставки.

После успешного HTTP отдельная транзакция проверяет lease, повторно читает платеж и сохраняет отметку доставки. Повторное чтение предотвращает потерю других обновлений платежа во время HTTP. После обычной успешной доставки конкурентный обработчик пропускает HTTP и сохраняется исходное время доставки.

Доставка имеет семантику at-least-once: при падении между успешным HTTP и commit отметки, а также после истечения lease, HTTP может повториться. Получатель должен обрабатывать дубли. POST содержит стабильный `X-Webhook-Delivery-Id`, равный UUID платежа; при повторе после успешного HTTP и неуспешного commit идентификатор сохраняется. См. [контракт webhook](webhook-delivery.md).

## Публикация Outbox

Worker захватывает одно доступное событие через `FOR UPDATE SKIP LOCKED`, сохраняет UUID владельца и срок lease и завершает транзакцию. RabbitMQ publisher вызывается без DB-транзакции. Пока он ожидает broker ack, другие workers могут захватывать остальные события; row locks и соединения для ожидания не нужны.

Срок lease равен `max(60, publish_timeout + 30)` секундам и отсчитывается по времени PostgreSQL. Каждый publish ограничен `publish_timeout`. После ack отдельная транзакция проверяет токен и срок, отмечает публикацию и снимает lease. Ошибки и quarantine тоже фиксируются отдельно для каждого события; backoff сохраняется. В пределах одного вызова `publish_batch` каждое событие рассматривается не более одного раза.

При отмене или ошибке БД снимается только свой lease. Если процесс завершился или cleanup не удался, событие доступно после истечения срока. Устаревший владелец не может подтвердить событие или снять чужой lease. Успешно подтвержденные события сохраняются при сбое последующих элементов пачки.

Если RabbitMQ принял сообщение, а commit отметки не состоялся, событие публикуется повторно с тем же `event_id` и `message_id`. Это сохраняет at-least-once; потребитель обязан допускать повтор сообщения. Exactly-once публикация не заявляется.

## Проверка и применение миграций

Для трех leases добавлены nullable-колонки в трех последовательных обратимых миграциях. Публичные статусы платежа и JSON-контракты API, RabbitMQ и webhook сохранены. При переходе между старой и новой реализацией workers нужно остановить, применить миграции и запустить согласованную версию: старые workers не проверяют leases.

Проверки используют отдельные PostgreSQL и RabbitMQ. В конкурентных сценариях внешние вызовы удерживаются событиями asyncio, а тест проверяет доступность row locks через `NOWAIT` и отсутствие занятых соединений. Восемь параллельных gateway-вызовов проверяются с пулом из одного соединения. Дополнительно проверяются таймауты, отмена, истечение leases, устаревшие владельцы и сбой между внешним успехом и commit. Это ограниченная конкурентная проверка, а не замер промышленной пропускной способности.

## Прикладные контракты

Сценарии и порты находятся в `src/payment_processor/application/`. Создание принимает `CreatePaymentCommand`; получение, обработка и доставка принимают UUID. Репозиторий получает платеж и payload события одним вызовом `save_with_outbox`, а commit выполняет общий scope.

Доменная сущность проверяет положительную конечную сумму в пределах `NUMERIC(18,2)`, поддерживаемую валюту, ключ длиной 1–255 символов и HTTP(S) webhook URL. Эти проверки применяются и при восстановлении из БД: некорректные значения отклоняются через `ValueError`, без округления и скрытого исправления. Согласованность исторических статусов и времён не исправляется автоматически: завершённый статус без `processed_at` не считается завершённым и не допускает успешной отметки webhook.

HTTP-ограничения описания, JSON и представления URL проверяются на границе API; схема события повторно проверяет транспортный payload до записи Outbox. Итоговые команды и результаты проверок приводятся отдельно в отчёте, а не в описании архитектуры.
